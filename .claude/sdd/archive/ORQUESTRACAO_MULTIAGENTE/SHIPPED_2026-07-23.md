## Summary

Grafo de orquestração que conecta os 5 agentes especialistas do blueprint (Classificador, Pesquisador Legal, Extrator de Regras, Determinístico, Sintetizador) numa pipeline fixa e auditável, usando LangGraph. Cada nó é uma função pura `State → State`, testável isoladamente; o nó Determinístico integra de verdade com `motor_calculo` (feature já shipada), enquanto os demais nós simulam o comportamento de LLM (ainda sem credenciais Claude/Vertex AI configuradas). O nó Classificador mascara CPF/CNPJ de verdade via regex — a única peça de PII desta feature, e não fake. O estado carrega um histórico auditável de todas as transições, o que é a base técnica da garantia de "100% auditável" do produto (`contexto.md`, seção 1.1). Esta é a primeira feature do projeto que conecta os componentes anteriores (`ingestion/` e `motor_calculo/`) num sistema, em vez de peças isoladas.

## Lessons Learned

### Process

- Reaproveitar o padrão de "import lazy para lib não instalável" (já usado com `typer`/`qdrant-client` na feature de ingestão) tornou a decisão de arquitetura quase automática desta vez — o padrão já estava validado, só precisou ser aplicado de novo ao `langgraph`.
- Esta foi a feature mais rápida até agora (brainstorm → ship no mesmo dia) — sinal de que reaproveitar schemas e padrões já validados (Chunk, ResultadoCalculo, Protocol+fake) reduz o tempo de design significativamente a cada ciclo.

### Technical

- **Um teste de acceptance criteria pegou um bug de segurança real**: o código do nó Classificador — copiado quase literalmente do Pattern 2 do próprio DESIGN — logava o texto original (com PII) no histórico auditável, em vez do texto já mascarado. Isso só foi descoberto porque o `test_at003` verificava explicitamente a ausência do CPF em *todas* as entradas do histórico, não só no campo `texto_mascarado`. Lição: quando uma exigência de segurança/privacidade existe (aqui, "nunca vaze PII"), o teste de aceitação deve verificar isso em *todos* os lugares onde o dado poderia vazar, não só no campo óbvio.
- Pydantic v2 aceita dataclasses (`ResultadoCalculo`) como campo de `BaseModel` com `arbitrary_types_allowed=True` — útil para não ter que reescrever tipos já validados em outras features como Pydantic puro.

### Communication

- O usuário decidiu prosseguir com o `/ship` mesmo com o blocker do `langgraph` documentado, diferente da feature de ingestão (onde o `/ship` ficou pendente). A diferença: aqui o blocker é "instalar uma lib", ali era "obter credenciais de infraestrutura de terceiros" — vale manter essa distinção em mente ao decidir se um blocker impede o ship ou é só um follow-up razoável.

### Tools & Libraries

- Nenhuma ferramenta nova além das já usadas — a feature reaproveitou integralmente `pydantic`, `pytest`, `ruff` já configurados.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| `langgraph` real | Instalar a lib num ambiente com controle do usuário e rodar `construir_grafo()` de verdade como teste E2E manual |
| Nós de LLM reais | Quando houver credenciais Claude/Vertex AI, substituir a classificação de intenção (Classificador), o Pesquisador Legal, o Extrator e o Sintetizador por chamadas reais — os fakes já retornam no schema correto, então a troca deve ser incremental, nó por nó |
| Integração com `ingestion/` real | O Pesquisador Legal fake deveria virar uma busca real no Qdrant assim que `PIPELINE_INGESTAO_LEGAL` for shipada (credenciais GCP/Qdrant pendentes) |
| API HTTP | Expor `construir_grafo()` via um endpoint (`/v1/tax/simulate`, seção 8 do blueprint) é o próximo passo natural depois que os nós de LLM forem reais |
