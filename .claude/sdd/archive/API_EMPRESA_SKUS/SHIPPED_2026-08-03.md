## Summary

Dá vida à tabela `empresa_skus` — schema e RLS aplicados desde `SCHEMA_POSTGRESQL` (2026-07-27),
mas nunca lida nem escrita por nenhuma rota até esta feature. Endpoint dedicado `/v1/tax/skus`
com CRUD completo (criar, listar paginado, consultar, editar, excluir) e upload em lote via CSV
síncrono (upsert por linha, relatório por linha, teto de 10.000 linhas). Uma migração nova (014)
corrige um gap real do schema original: `ncm_code` era `NOT NULL` para toda SKU, mesmo de
serviço — agora há uma coluna `natureza` (mesmo vocabulário de `ItemSimulacao`) e um `CHECK` que
garante exatamente um dos dois códigos (NCM xor NBS) preenchido.

Além do CRUD, `/v1/tax/simulate` passa a resolver `ncm`/`nbs` a partir do `sku` cadastrado quando
ambos vierem ausentes do item — o valor explícito no payload sempre vence sobre o catálogo, e um
SKU de mercadoria não cadastrado sem `ncm` explícito recebe 422 claro (nunca simula com NCM
vazio). Esta é a **primeira feature do projeto com CRUD de escrita multi-tenant** desde o schema
original — toda feature anterior só lia tabelas públicas de referência (legislação, TIPI, Anexos
de redução), sem dimensão de tenant nenhuma.

**Achado técnico do `/brainstorm`, ausente do roadmap**: o schema previa `ncm_code NOT NULL` sem
nenhuma coluna `natureza` — um SKU de serviço puro precisaria de um NCM inventado sem a migração
014. **Dois achados reais do `/build`**: (1) `psycopg` não era importável neste sandbox de
desenvolvimento, e o router não podia depender do tipo concreto da exceção — corrigido checando o
atributo `sqlstate` (padrão do protocolo Postgres) em vez de `psycopg.errors.UniqueViolation`; (2)
a suíte de testes já existente revelou que "SKU de serviço sem `nbs`" sempre foi um estado válido
(pré-feature, `nbs` já era opcional) — o 422 de "não resolvido" foi restrito a `MERCADORIA`, a
única natureza que realmente ganhou uma lacuna nova com esta feature.

**Revisão de segurança dedicada** (recomendada pelo `/define`, dado o risco novo de vazamento
cross-tenant): nenhum vazamento confirmado — a disciplina `sessao_do_tenant` foi aplicada
corretamente nas 7 funções novas. 5 achados reais, 3 corrigidos na mesma sessão (validação de
formato de NCM/NBS no CRUD individual, teto de tamanho de arquivo antes do parsing do CSV,
tratamento de arquivo não-UTF-8), 2 registrados como recomendação de trabalho futuro (gap
pré-existente em `resolver_tenant`; ausência de rate limiting em toda a API).

## Lessons Learned

### Process

- **Verificar o schema real ANTES do `/brainstorm`** (em vez de confiar na descrição de uma linha
  do roadmap) encontrou o gap de `natureza` ausente antes de qualquer código ser escrito — a
  mesma disciplina de "nunca presumir, sempre verificar" que já regia a leitura de legislação
  nas features anteriores, aqui aplicada a SCHEMA em vez de TEXTO LEGAL.
- **Rodar a suíte de testes já existente logo depois do primeiro wiring em `/v1/tax/simulate`**
  (em vez de só escrever os testes novos e assumir sucesso) encontrou uma regressão real — 7
  testes pré-existentes falhando por um pressuposto errado (SERVICO sem `nbs` sempre precisar de
  resolução). Testar contra o comportamento JÁ EXISTENTE é o único jeito confiável de descobrir
  qual parte do "novo" na verdade já era permitido antes.
- **Uma revisão de segurança dedicada, pedida no `/define` e executada de fato antes do `/ship`**
  (não só mencionada como boa prática) encontrou 3 problemas reais que nenhum dos testes
  funcionais capturaria (validação assimétrica entre CRUD e CSV; leitura de arquivo antes do
  limite; decode sem tratamento) — vale repetir para toda feature futura que introduza um novo
  tipo de escrita ou uma nova superfície de entrada de arquivo/usuário.

### Technical

- **Dependência de um driver de banco (`psycopg`) só para TIPAR uma exceção é mais frágil que
  necessário** — checar o atributo `sqlstate` (garantido pelo protocolo Postgres, não uma
  peculiaridade do driver) desacopla o código do pacote estar instalável, e permitiu testar o
  caminho de conflito (409) com um fake simples, sem precisar instalar infraestrutura real neste
  ambiente de desenvolvimento.
- **`(xmax = 0)` num `INSERT ... ON CONFLICT ... RETURNING` é o jeito atômico de distinguir
  criação de atualização** — evita um `SELECT` prévio (condição de corrida) só para saber se o
  registro já existia, e ficou testado tanto contra Postgres real quanto contra um fake com
  armazenamento em memória.
- **Um campo opcional que se torna necessário SÓ EM PARTE do domínio (aqui, `ncm` só realmente
  precisa de resolução para MERCADORIA, nunca para SERVICO) precisa de tratamento assimétrico
  explícito** — tratar os dois lados do `natureza` da mesma forma por padrão é o tipo de suposição
  que só a execução real contra a suíte de testes revela.

### Communication

- **Registrar decisões tomadas por julgamento (não por confirmação direta do usuário) como
  Assumptions explícitas no `/define`** (A-002/A-003, precedência SKU e semântica de upsert)
  permitiu avançar sem bloquear o fluxo, mantendo total rastreabilidade de que aquelas decisões
  poderiam ser revisadas — nenhuma delas precisou de correção, mas o registro existia caso
  precisasse.

## Recommendations for Future Work

| Area | Recommendation |
|------|-----------------|
| `resolver_tenant` sem checar `ativo` no atalho de UUID | Achado do `security-reviewer` — função compartilhada por toda a API (não só esta feature); vale uma sessão dedicada, já que agora autoriza ESCRITA, não só leitura |
| Rate limiting | Nenhum endpoint do projeto tem — o upload CSV é o primeiro a tornar isso relevante de verdade (até 10.000 round-trips por request); candidato a feature própria de infraestrutura |
| `FILA_ASSINCRONA_CELERY_REDIS` (posição 11 do roadmap) | Próxima etapa natural para volumes acima de 10.000 SKUs — esta feature deliberadamente não tentou resolver esse caso |
| Frontend | `frontend/` ainda não expõe `/v1/tax/skus` na UI — mesma pendência já registrada em todos os SHIPPEDs anteriores |
| Roadmap | Restam as posições 4-11 da "primeira leva" (`LLM_REAL_VERTEX_AI`, `ORQUESTRACAO_NOS_REAIS`, `REMOVER_FAKE_HISTORICO`, `CLOUD_COMPOSER_PROVISIONAMENTO`, `VERIFICACAO_FRONTEND_NAVEGADOR`, `DIAGNOSTICO_BUSCA_HIBRIDA`, `BIGQUERY_DATA_WAREHOUSE`, `FILA_ASSINCRONA_CELERY_REDIS`) |
