## Summary

7ª posição do `ROADMAP_SEQUENCIA_AUDITORIA_2026-07.md`: proveu, contra um ambiente Cloud
Composer 3 real (nunca provisionado até esta feature), se `dags/ingestao_legal_dag.py`
(escrita em `INGESTAO_TCU_E_ETL_AIRFLOW`, sempre validada só por revisão de código porque
`apache-airflow` não instala no sandbox de desenvolvimento) roda de verdade. Diferente de todas
as features anteriores de infraestrutura real do projeto, o custo contínuo do Composer
(~US$300-400/mês, achado do `/brainstorm`) era desproporcional a uma DAG que roda só ~2
tasks/semana — o usuário decidiu explicitamente por um ciclo **efêmero**: provisionar via
Terraform, verificar a DAG rodando de verdade, capturar evidência, e destruir o ambiente no
mesmo dia, não deixá-lo permanente como todo recurso GCP anterior do projeto. O ciclo revelou 8
bugs reais de infraestrutura/CI (permissões IAM, sintaxe de CLI do Airflow, sincronização
assíncrona entre scheduler/workers do GCS, e um bug real de interpolação de shell no GitHub
Actions) — todos corrigidos — antes de travar num bloqueio final não atribuível a bug de
código: o worker do Composer parece ficar sem memória ao carregar o modelo de embedding
(`multilingual-e5-large`, ~1-2GB em ONNX), e tentar corrigir isso redimensionando o ambiente
(SMALL → MEDIUM) deixou o webserver do Airflow em crash-loop sustentado por mais de 10 horas.
Dado o custo real já acumulado e a ausência de sinal de recuperação, a decisão foi documentar o
bloqueio (mesma disciplina da quota do Vertex AI em `LLM_REAL_VERTEX_AI`) e destruir o ambiente
— o que foi confirmado (`terraform apply`: 5 recursos destruídos, custo zerado).

## Lessons Learned

### Process

- Um ciclo efêmero de infraestrutura (provisionar → verificar → destruir no mesmo dia) é um
  padrão novo e válido quando o custo contínuo de um recurso é desproporcional ao seu uso real —
  mas o orçamento de TEMPO precisa ser generoso: o que parecia ser "verificar uma DAG" se tornou
  uma sessão de ~14 horas de relógio, a maior parte esperando infraestrutura real (criação do
  ambiente, sincronizações assíncronas, um resize que nunca estabilizou).
- Redimensionar um ambiente Cloud Composer já provisionado (`environment_size` +
  `workloads_config`) NÃO é uma ação rápida de "mais um apply" — é uma operação estrutural que
  pode levar horas e deixar o ambiente temporariamente (ou, neste caso, indefinidamente dentro
  da janela observada) instável. Num ciclo efêmero orçado a horas, não a dias, essa tentativa de
  correção acabou custando mais do que teria custado simplesmente provisionar o tamanho maior
  desde o início.
- Quando um teste automático (aqui, o polling do status da DAG) reporta falha em segundos para
  uma operação que deveria levar minutos, isso é sinal do TESTE estar quebrado, não
  necessariamente da operação real — vale sempre checar a plausibilidade do tempo decorrido antes
  de aceitar o veredito.

### Technical

- `gcloud composer environments storage dags import --source=DIR` (fonte = diretório) não copia
  recursivamente de forma confiável — enviar arquivo por arquivo (`find ... | while read`) com
  `--destination` explícito é o padrão seguro.
- O scheduler e os workers de um ambiente Composer sincronizam a pasta GCS de DAGs de forma
  **independente** — o scheduler "ver" a DAG não significa que o worker que vai executar a task
  já sincronizou os módulos que ela importa. Um `sleep` de buffer entre upload e disparo é
  necessário.
- `airflow dags list_dag_runs` (underscore) é sintaxe do Airflow 1.x; `composer-3-airflow-2` usa
  `list-runs` (hífen). Com stderr suprimido, o comando errado falha silenciosamente sem nenhuma
  pista — nunca suprimir stderr de comandos de CLI desconhecidos até ter certeza da sintaxe certa
  na versão em uso.
- Interpolar `${{ inputs.x }}` do GitHub Actions DIRETO dentro de uma atribuição bash
  (`VAR="${{ inputs.x }}"`) quebra quando o valor de `x` contém aspas internas — o YAML substitui
  o texto cru antes do bash tokenizar. Passar por um bloco `env:` evita a re-tokenização (o bash
  lê a variável de ambiente já pronta).
- Grepar uma tabela de histórico INTEIRA (`dags list-runs`) por uma string de status
  (`success`/`failed`) é uma armadilha real quando há tentativas anteriores na mesma tabela — o
  grep casa com a linha errada. A correção correta é sempre filtrar pelo identificador único da
  execução específica (aqui, o `run_id` capturado do próprio output do comando de disparo).
- `Worker (pid:N) was sent SIGKILL! Perhaps out of memory?` + `WORKER TIMEOUT` nos logs do
  Gunicorn é o sinal inequívoco de esgotamento de memória no processo — mesma assinatura de
  diagnóstico já usada com sucesso em `LLM_REAL_VERTEX_AI` (lá, no Cloud Run; aqui, no webserver
  do Composer), reforçando que "ver o log real" continua sendo o único jeito confiável de
  diferenciar um bug de código de um limite de recurso de infraestrutura.

### Communication

- Múltiplos check-ins explícitos (`AskUserQuestion`) antes de cada nova rodada de custo real
  (retry de apply, resize do ambiente, continuar após um bloqueio) mantiveram o usuário no
  controle das decisões de custo/tempo — nenhuma decisão de gastar mais dinheiro real foi tomada
  unilateralmente.

### Tools & Libraries

- `gcloud composer environments run ENV -- <comando airflow>` é o único jeito de rodar CLI do
  Airflow contra um ambiente gerenciado sem acesso direto ao cluster — mas cada chamada paga o
  custo de estabelecer uma sessão de exec via GKE, o que a torna lenta e, quando o ambiente está
  instável, pode levar minutos por chamada (explica por que os retries do loop de descoberta
  demoraram muito mais que os `sleep 15` configurados).

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Se este ciclo for repetido | Provisionar direto com `ENVIRONMENT_SIZE_MEDIUM` (ou maior) desde o início, evitando a necessidade de um resize ao vivo — o custo por hora é maior, mas o tempo total (e portanto o custo total) do ciclo efêmero provavelmente seria menor |
| `dags/ingestao_legal_dag.py` | Considerar um modo de teste que não carregue o modelo de embedding completo (ex: mock do `HybridEmbedder` para a verificação de infraestrutura), separando "a DAG importa e orquestra corretamente" de "o modelo de embedding cabe na memória do worker" — dois riscos distintos que esta feature não conseguiu isolar |
| `verificar_composer_producao.yml` | Já corrigido nesta sessão (filtro por `run_id` exato) — herda o achado para qualquer reuso futuro |
| Cloud Composer em geral | Se o projeto algum dia justificar um ambiente permanente, orçar workloads_config com folga generosa de memória desde o Terraform inicial, não como ajuste reativo |
