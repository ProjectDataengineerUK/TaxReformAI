## Lessons Learned

### 1. "Documente tudo" tinha uma pergunta escondida dentro

O usuário pediu alíquotas vigentes "por se tratar de transição" — uma frase de seis palavras que
revelou que a simulação de 2026 mostrava um valor líquido sem dizer que ele é compensável, e sem
calcular contra o quê. A lição não é sobre código: é que perguntas curtas do usuário sobre o domínio
às vezes valem mais que qualquer revisão de código, porque vêm de quem entende o negócio.

### 2. Memória de lei tributária é seguramente errada até prova em contrário

Nesta feature, cada uma das 7 alíquotas foi lida do texto oficial antes de virar código — não porque
fosse óbvio que precisava, mas porque a sessão já tinha dois precedentes de erro por confiar em
memória (o art. 474 da LCP 214, tratado por engano como redução geral de ICMS/ISS; o BAAI/bge-m3,
que não existe no fastembed). O hábito formado: toda vez que uma alíquota "óbvia" apareceu na
cabeça, ela foi conferida contra o Planalto/LexML antes de virar linha de código. Nenhuma das 7
precisou de correção depois — o que sugere que o hábito, não a sorte, é o que evitou o oitavo erro.

### 3. Cloud SQL não é "Postgres com um endereço IP diferente"

O achado mais caro desta feature: nenhum papel no Cloud SQL — nem `postgres` — tem `rolsuper=true`.
Uma migração escrita e testada corretamente contra um `postgres:16` genérico (onde a distinção
superusuário/comum é real e teach RLS-bypass de verdade) falhou no ambiente gerenciado porque a
plataforma resolve esse problema de um jeito estrutural diferente. A migração tentava "confirmar o
óbvio" (que um papel não tem SUPERUSER) e essa confirmação, especificamente, exige SER superusuário
— uma pegadinha do próprio Postgres, não do Cloud SQL.

**Lição prática:** ao portar uma migração/config testada contra Postgres genérico para um serviço
gerenciado (Cloud SQL, RDS, etc.), qualquer coisa que toque em atributos de papel (não em privilégios
de objeto) merece diagnóstico direto contra o ambiente real antes de assumir que o comportamento é
igual.

### 4. Least privilege é uma escolha, não um efeito colateral do primeiro erro

A verificação do audit log em `deploy.yml` precisou de acesso a uma senha do Postgres. O caminho mais
rápido teria sido reusar a senha do admin, que já estava sendo buscada em `migrar_banco.yml`. A escolha
foi conceder acesso à senha do **app** — mais restrita — porque a tarefa (um SELECT dentro da sessão de
um tenant) não precisa de privilégio de admin. Nenhuma das duas escolhas teria sido pega por teste
algum; a diferença é puramente de disciplina no momento da correção.

### 5. Cada camada de infraestrutura tem seu próprio conjunto de permissões, e nenhuma generaliza

Corrigir o deploy real exigiu conceder, em sequência, quatro permissões distintas a duas SAs
diferentes (`cloudsql.admin`+`secretmanager.admin` ao Terraform; `cloudsql.client` e acesso a um
secret específico ao deployer) — cada uma descoberta por um erro 403 diferente, nunca por antecipação.
Nenhum desses erros seria visível em CI, porque CI não tem SAs reais nem Cloud SQL real.

**Lição:** ao introduzir um novo recurso GCP que outra SA precisa acessar (Cloud Run → Cloud SQL,
Cloud Run → Secret Manager), o primeiro deploy real *é* o teste de permissões — não há como
simular isso antes.

### 6. `db/` não copiado para a imagem Docker é o mesmo erro do TCU, três features depois

Esta sessão já tinha corrigido "esquecer de copiar um diretório para dentro da imagem" nas features
anteriores (indiretamente, ao verificar o conteúdo de `api/Dockerfile`), e mesmo assim `db/` ficou de
fora na primeira vez que a API precisou dele. Pytest nunca pegaria isso: roda a partir da raiz do
repo, onde `db/` já está no `sys.path`. Só um `POST` real contra o contêiner revelou o
`ModuleNotFoundError`.

## Recommendations for Future Work

1. **PYTHONPATH e dependências mínimas em cada workflow que roda Python** — vale uma checklist
   explícita (`PYTHONPATH=${{ github.workspace }}` + instalar só o necessário) sempre que um workflow
   novo rodar um script Python fora do job principal de testes.
2. **Diagnosticar antes de portar** qualquer configuração de permissão/papel testada contra Postgres
   genérico para Cloud SQL (ou qualquer serviço gerenciado) — a Lição 3 vale para além desta feature.
3. **IPI (TIPI) e ICMS interno/ISS** seguem fora de escopo, mesma razão do SPED/IBPT: dado tabular,
   não alíquota codificável, sem fonte pública para IPI e sem norma única para os outros dois.
