## Summary

Interface web Next.js 14 (App Router) com duas páginas — `/simulador` (formulário estruturado por NCM/quantidade/valor, consumindo `/v1/tax/simulate`) e `/consulta` (pergunta em texto livre, consumindo `/v1/tax/query`) — mais um componente de configuração de API key persistida em `localStorage`. É a quinta e última peça central planejada do blueprint: `ingestion/`, `motor_calculo/`, `orquestracao/` e `api/` agora têm uma interface real consumindo-os. Esta feature também corrigiu um bug crítico de CORS ausente em `api/main.py` (`API_HTTP_SIMULACAO`) — sem isso, nenhuma chamada da UI a partir de um navegador real teria funcionado, um problema que só a verificação E2E desta feature (simulando um preflight de navegador via `curl`) revelou.

## Lessons Learned

### Process

- Quando o usuário pede explicitamente para "deixar tudo montado" em vez de responder a uma sequência longa de perguntas, o caminho certo não é pular a exploração — é documentar as decisões técnicas diretamente (como se o usuário as tivesse delegado) e pedir **uma** confirmação da síntese completa, em vez de várias perguntas fragmentadas. O brainstorm desta feature seguiu esse padrão e funcionou bem.
- Node.js/npm disponíveis no sandbox tornaram esta feature (e a anterior, `API_HTTP_SIMULACAO`) sensivelmente mais rápidas de construir e verificar que as duas primeiras (`PIPELINE_INGESTAO_LEGAL`, `ORQUESTRACAO_MULTIAGENTE`), que enfrentaram bloqueios de instalação em Python. Vale checar a disponibilidade real do toolchain de uma stack **antes** de comprometer-se com uma decisão de design que dependa dela.

### Technical

- **A verificação E2E revelou um bug que nenhum teste automatizado (mockado) nem checagem via `curl` direto conseguiria pegar**: CORS é uma restrição aplicada pelo *navegador*, não pelo servidor nem por ferramentas de linha de comando. Só simular um preflight `OPTIONS` com o header `Origin` (o que um navegador real enviaria) expôs que `api/main.py` não tinha `CORSMiddleware`. Lição: ao construir um frontend que chama uma API de origem diferente, testar explicitamente o comportamento de preflight é necessário — testes que mockam a camada de rede escondem esse tipo de problema por definição.
- Ferramentas de CLI de terceiros (como o Shadcn) podem mudar de comportamento entre versões de forma incompatível com o uso planejado — importante ter um fallback já pensado (Decision 4 do DESIGN preveriu isso) em vez de descobrir o problema no meio do build sem plano B.

### Communication

- Nenhuma pergunta de esclarecimento foi necessária no `/define` (Clarity Score 14/15) — o brainstorm, mesmo abreviado a pedido do usuário, ainda cobriu os pontos essenciais de escopo.

### Tools & Libraries

- `@testing-library/react` + Vitest permitiram testar o comportamento de erro (401/422) sem precisar de um backend real rodando durante os testes — mas a verificação de CORS exigiu especificamente `curl` simulando um navegador, algo que nenhuma dessas ferramentas de teste de componente cobre.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Verificação em navegador real | Testar manualmente com a extensão Claude in Chrome conectada, ou pedir ao usuário para validar o fluxo completo no navegador dele |
| CORS em produção | `FRONTEND_ORIGINS` está com default de desenvolvimento (`localhost:3000`) — configurar para o domínio real antes de qualquer deploy |
| Shadcn real | Se o CLI mais antigo/compatível for necessário no futuro, considerar pin de versão (`npx shadcn@4.13.0`) em vez do fallback manual |
| Componentes de UI | Uma vez que existam mais páginas, extrair os componentes `ui/*` para um pacote compartilhado ou reconsiderar adotar Shadcn de verdade com uma versão compatível |
