## Summary

A API já calculava o regime tributário atual (PIS/COFINS, ICMS interestadual/interno, ISS, IPI) desde `SCHEMA_POSTGRESQL`/`IPI_TIPI_MOTOR_CALCULO`, mas nenhuma tela exibia esse dado — o usuário notou o gap diretamente ("foi ingerido a legislação atual e não tem nenhuma tabela trazendo a comparação"). Esta feature fecha o gap dos dois lados: `/simulador` passa a exibir uma tabela comparativa regime atual x IVA Dual (agregada e por item, citando fonte legal), e `/consulta` — que antes nem calculava o regime atual, por ter um payload agregado (`valor_base` único) sem UF/natureza/NCM por item — foi redesenhado para aceitar itens estruturados com paridade total de cálculo em relação ao `/simulador` (mesmos Anexos de redução, mesmo IPI por item). A peça central da implementação foi extrair as ~700 linhas de lógica de `api/routers/simulate.py::simular()` para uma função pura reaproveitável (`api/simulacao.py::calcular_simulacao_completa()`), eliminando a duplicação que a paridade exigiria, e redesenhar o guardrail do sintetizador para verificar só totais agregados (nunca por item) — resolvendo, ANTES de escrever qualquer código, um risco real de regressão que a investigação prévia identificou.

## Lessons Learned

### Process

- **Investigar a suposição mais arriscada ANTES de tocar em qualquer arquivo compensa.** O DEFINE marcou explicitamente a Assumption A-004 (guardrail do sintetizador com resultado itemizado) como a primeira coisa a resolver no `/design` — e essa investigação (ler `sintetizador.py` linha a linha antes de desenhar qualquer schema novo) mudou a arquitetura inteira do guardrail antes que qualquer código fosse escrito. Sem isso, o build teria produzido um guardrail que rejeitaria quase todo parecer real com mais de um item.
- **Um brainstorm de 8 perguntas para uma feature que parecia simples ("adicionar uma tabela") revelou que ela não era simples.** O pedido original do usuário foi "por que não existe uma comparação" — cada pergunta subsequente (escopo `/consulta`, itens vs. valor único, paridade de precisão) dobrou o tamanho real do trabalho. Vale a pena deixar o brainstorm forçar essas perguntas mesmo quando o pedido parece pequeno.

### Technical

- **Extração literal de função é mais segura que reescrita.** Em vez de reimplementar a lógica de `simular()` a partir do entendimento do que ela faz, a extração usou um script Python para fatiar as linhas exatas do arquivo original e aplicar só as substituições textuais mínimas necessárias (troca de `payload.X` por `X`, troca de `HTTPException` por exceções de domínio). Isso reduziu a superfície de erro de transcrição a quase zero — confirmado pelos 7 testes pré-existentes de `test_api_simulate.py` passando sem nenhuma mudança de conteúdo (AT-007).
- **Checar substring "0" como prova de integridade é uma armadilha silenciosa.** Ao desenhar o guardrail agregado, incluir campos que podem ser `Decimal("0")` (ex: `total_icms_interno` quando o payload é só interestadual) criaria uma verificação que sempre passa trivialmente — "0" é substring de quase qualquer texto numérico. Corrigido pulando valores zero, não só `None`, do conjunto verificado.
- **Um teste de paridade que só executa a asserção "se status == 200" pode passar sem testar nada.** A primeira versão do teste AT-003/AT-008 usava um parecer fake ESTÁTICO válido só para o payload padrão do arquivo; para o payload de paridade (diferente), o guardrail rejeitava (503) e a asserção de igualdade nunca rodava — o teste "passava" sem provar nada. Corrigido construindo o fake dinamicamente a partir dos números reais devolvidos pelo `/v1/tax/simulate`, forçando a asserção a sempre executar.

### Communication

- Nenhuma pergunta ficou sem resposta explícita — as 8 perguntas do brainstorm e a pergunta extra sobre o campo `valor_base` derivado evitaram um retrabalho real: se `valor_base` tivesse ficado como campo duplicado (manual + itens), o `/build` teria precisado escolher qual fonte de verdade usar sem orientação do usuário.

### Tools & Libraries

- **Fatiar o arquivo original com Python (não reescrever manualmente) para a extração da função.** Garantiu fidelidade byte a byte no corpo da função extraída, o que o `ruff`/`pytest` sozinhos não teriam verificado com a mesma confiança.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| `/consulta` — precisão | Considerar limitar o número de itens aceitos em `/consulta` de forma diferente de `/simulador` (hoje ambos usam `max_length=100` de `ItemSimulacao`) — o `/consulta` ainda paga o custo de uma chamada LLM por request, então payloads muito grandes podem gerar prompts longos para o sintetizador |
| Guardrail | Se um dia o produto precisar que o parecer narre TAMBÉM o detalhamento por item (não só o agregado), reavaliar a Decision 5 — hoje ela assume deliberadamente que o detalhamento fica só na UI, nunca na prosa do LLM |
| Frontend | `ComparativoRegime.tsx` duplica alguns dados já mostrados nos cards existentes (valor líquido, SKU) — cabe uma decisão de design visual futura sobre unificar os cards em vez de mostrar a mesma informação duas vezes na mesma tela |
