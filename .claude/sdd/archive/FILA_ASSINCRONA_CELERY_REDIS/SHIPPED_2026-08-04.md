## Summary

11ª e última posição da "primeira leva" do `ROADMAP_SEQUENCIA_AUDITORIA_2026-07.md` — com esta
feature, a sequência inteira pós-auditoria (`SCHEMA_POSTGRESQL` → posições 1-11) está completa.
O nome preserva o rótulo original do roadmap ("Celery/Redis"), mas o mecanismo real é **Cloud
Tasks**: um `/brainstorm` de duas rodadas descobriu que Memorystore Redis exige VPC + Serverless
VPC Access connector (custo real ~US$60-70/mês, primeiro recurso do projeto a sair da disciplina
"sem VPC"), e trocou para Cloud Tasks + um endpoint interno no mesmo serviço Cloud Run da API —
sem Redis, sem VPC, sem worker dedicado. `POST /v1/tax/skus/upload` passou a ser **sempre
assíncrono** (`202` + `job_id` imediato), com status rastreado numa tabela Postgres nova
(`sku_upload_jobs`, RLS por tenant) em vez de um result backend externo.

A feature corrigiu 3 achados reais de infraestrutura (permissão de IAM do Cloud Tasks,
delimitador de env vars colidindo com um e-mail de service account, OOM de memória) — mas
encontrou um QUARTO achado real que **não foi corrigido**: mesmo com a memória do container
dobrada (4Gi→8Gi), um upload real de 55.000 linhas esgotou o pool de conexões do Postgres
(`psycopg_pool.PoolTimeout`) após ~20 minutos de carga sustentada contra a instância `db-f1-micro`
do Cloud SQL — revelando que a arquitetura de "uma chamada HTTP processa o arquivo inteiro,
uma transação por linha" não sustenta a meta de 50.000+ SKUs do blueprint. Em vez de insistir em
mais correções não comprovadas, a decisão de engenharia foi reverter o teto de linhas de volta
para 10.000 (o mesmo da versão síncrona anterior) — a feature entrega o ganho real e comprovado
(upload nunca mais bloqueia o cliente) sem reivindicar uma escala que não foi provada.

## Lessons Learned

### Process

- **Teste de carga real no volume-alvo não é opcional — é barato relativo ao custo de prometer
  algo quebrado.** O smoke test desta feature (1 linha) provou ZERO sobre a alegação central do
  blueprint ("50.000+ SKUs"). Só um teste real no volume-alvo (55.000 linhas, ~US$ desprezível em
  Cloud Run/Cloud SQL, ~1h de tempo de sessão) revelou dois bugs reais e distintos que nenhuma
  revisão de código ou teste em pequena escala jamais encontraria.
- Quando uma segunda tentativa de correção falha por uma causa DIFERENTE da primeira (aqui: OOM
  corrigido, depois pool de conexões esgotado), isso é sinal de que o problema é estrutural
  (arquitetura), não um bug pontual — vale parar de tentar "só mais um ajuste" e reavaliar a
  abordagem, em vez de entrar numa espiral de correções não comprovadas sob pressão de custo.
- Reduzir uma promessa (teto de 100.000 para 10.000) é uma escolha de engenharia legítima e mais
  honesta do que manter um número que não foi comprovado — mesma disciplina de "nunca estimar,
  nunca falhar em silêncio" já aplicada a alíquotas tributárias, agora aplicada a limites de
  sistema.

### Technical

- Um container Cloud Run compartilha memória entre TODAS as suas rotas — uma feature que carrega
  um modelo pesado (embedding, ~2GB) para uma rota deixa menos memória disponível para qualquer
  OUTRA rota do mesmo serviço, mesmo que não relacionada. Bugs de memória em produção podem vir
  de uma feature completamente diferente da que está sendo testada.
- `psycopg_pool.PoolTimeout` sob carga sustentada é sintoma de VAZÃO do banco, não
  necessariamente de um vazamento de conexão no código da aplicação — uma instância `db-f1-micro`
  processando milhares de transações individuais em sequência é um gargalo estrutural real, que
  nenhum ajuste de código sozinho resolve (exigiria batching de escritas ou um tier maior de
  banco).
- Interpolar `${{ inputs.x }}` do GitHub Actions dentro de um delimitador customizado
  (`--set-env-vars="^X^..."`) quebra se QUALQUER valor contiver o próprio caractere delimitador —
  um e-mail de service account (`@`) é um exemplo real e fácil de não antecipar; `|` é uma escolha
  mais segura para esse padrão neste projeto.
- Cloud Tasks + verificação manual de token OIDC no código (em vez de `--no-allow-unauthenticated`
  na borda do Cloud Run) é o padrão certo quando o mesmo serviço também serve rotas públicas —
  funcionou corretamente na primeira tentativa real, sem achados de segurança.

### Communication

- Um `/brainstorm` de duas rodadas (a primeira aceitando Celery+Redis, a segunda revertendo para
  Cloud Tasks depois de um achado de custo/complexidade real) mostra o valor de reabrir uma
  decisão já tomada quando um fato novo e material muda o quadro — não é indecisão, é resposta a
  informação nova.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Meta de 50.000+ SKUs | Requer particionar um upload grande em MÚLTIPLAS Cloud Tasks menores (lotes de 2.000-5.000 linhas cada), não uma única chamada processando tudo — trabalho real, não mais opcional |
| Job travado em `PROCESSANDO` após crash | Um `SIGKILL` (OOM ou outro) nunca aciona o `except` do endpoint interno, deixando o job preso para sempre sem sinal de erro — precisa de um mecanismo de detecção de job "zumbi" (timeout no cliente, ou um job de limpeza periódico) |
| Artefatos órfãos em produção | 2 jobs travados (`df4900b9-...`, `3793a83c-...`) e um número não determinado de linhas `SMOKE-50K-*` em `empresa_skus` — limpeza manual pendente, custo de armazenamento desprezível |
| Cloud SQL `db-f1-micro` | Se volumes de escrita em lote continuarem crescendo (não só este upload), reavaliar o tier da instância — decisão de custo/produto, não técnica |
