## Summary

API FastAPI com dois endpoints: `POST /v1/tax/simulate` (estruturado, schema idêntico ao exemplo da seção 8 do blueprint, pensado para integração com ERP) e `POST /v1/tax/query` (conversacional, expõe o grafo de orquestração via uma pergunta em texto livre). Autenticação mínima via header `X-API-Key` validado contra uma lista em variável de ambiente. Esta feature conecta os três componentes anteriores (`ingestion/`, `motor_calculo/`, `orquestracao/`) num serviço HTTP real pela primeira vez no projeto — e é a primeira das quatro features shipadas sem nenhum blocker de dependência não instalável, verificada tanto por testes automatizados quanto por um servidor `uvicorn` real respondendo a `curl`.

## Lessons Learned

### Process

- Esta foi a primeira feature das quatro sem nenhum blocker de infraestrutura — o ciclo completo (brainstorm → ship) ficou visivelmente mais rápido e sem as ressalvas de "não pude testar contra a lib real" que apareceram em todas as anteriores. Vale notar como sinal: quando a stack de uma feature já está disponível no ambiente, o ritmo do SDD acelera bastante.
- Resolver a tensão de design mais cedo (o exemplo da seção 8 do blueprint usar um ano sem alíquota confirmada) evitou que ela virasse uma surpresa durante o build — foi identificada e decidida já na fase de Design (Decision 3), então o Build só precisou implementar o que já estava combinado.

### Technical

- **Um requisito do DEFINE quase não foi verificado corretamente por causa de uma sutileza do framework**: `Header(...)` (obrigatório) no FastAPI intercepta headers ausentes com um 422 de validação *antes* da lógica de autenticação rodar — só headers presentes chegam à função da dependency. Como o DEFINE pedia 401 tanto para ausência quanto para invalidez, isso exigiu trocar para `Header(None)` opcional e checar `None` manualmente. Lição: ao definir "deve retornar código X", vale testar explicitamente o caminho de "campo ausente" separado de "campo inválido" — frameworks web costumam tratar os dois de formas diferentes por padrão.
- Promover um helper de teste (`executar_grafo_sequencial`) para um módulo de produção (`orquestracao/executor.py`) foi direto porque a função já não tinha nenhuma lógica específica de teste misturada — só encadeava chamadas reais. Isso é um sinal de que o helper foi bem escrito desde o início.

### Communication

- Nenhuma pergunta de esclarecimento foi necessária durante o `/define` (Clarity Score 14/15 direto) — o brainstorm anterior já tinha resolvido todas as ambiguidades de escopo, incluindo a mais importante (dois endpoints, não um).

### Tools & Libraries

- `fastapi.testclient.TestClient` (usa `httpx` por baixo) permitiu testar os endpoints sem subir um servidor — e depois um `uvicorn` real rodado em background + `curl` serviu como confirmação adicional de que o comportamento é o mesmo num servidor de verdade, não só no `TestClient`.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Conectar `langgraph` real | Quando a lib estiver instalável, `api/routers/query.py` pode trocar `executar_consulta()` por `construir_grafo().invoke()` sem mudar o contrato da API |
| Conectar LLMs reais | Os fakes em `orquestracao/nos/` continuam sendo o gargalo para tornar o endpoint conversacional "real" — feature futura quando houver credenciais Claude/Vertex AI |
| Conectar Qdrant real | O `PIPELINE_INGESTAO_LEGAL` (ainda não shipado) precisa das credenciais GCP/Qdrant para o Pesquisador Legal deixar de ser fake |
| Multi-tenancy real | Quando o schema Postgres (seção 7 do blueprint) existir, a API pode evoluir de "lista de chaves em config" para autenticação/autorização reais por tenant |
| Segurança | API keys não são hasheadas nem rotacionadas — antes de qualquer uso além de demo/MVP interno, vale uma revisão dedicada de `@security-reviewer` |
