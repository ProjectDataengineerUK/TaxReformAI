## Summary

Segunda implementação real de `LegalSource` (TCU, via Resoluções em PDF extraídas com `pdftotext`) e a DAG do Airflow/Cloud Composer (TaskFlow API) que o blueprint (`contexto.md`, seção 4.2/5.2) já previa como orquestrador oficial, substituindo a CLI manual de `ingestion/pipeline.py`. A feature prova que a arquitetura construída em `PIPELINE_INGESTAO_LEGAL` (protocolo `LegalSource`, `Lei.artigos_soltos`, `chunker.gerar_chunks()`) já era genérica o bastante para uma segunda fonte em formato completamente diferente (PDF, não HTML) sem precisar modificar `chunker.py`/`chunk_models.py`. `apache-airflow` não é instalável neste sandbox (mesmo bloqueio de `qdrant-client`/`fastembed`/`langgraph`) — a DAG é escrita com sintaxe real de produção e validada por revisão de código, não por execução, decisão explícita documentada desde o brainstorm.

## Lessons Learned

### Process

- Verificar a premissa do brainstorm ("PDF já baixado") *antes* de escrever qualquer código no Design evitou descobrir o problema só na hora do Build — o `find` que rodei no início do `/design` mostrou que o PDF de uma sessão anterior não existia mais neste ambiente, e já baixei um substituto real (Resolução TCU 388/2026) com tempo de sobra para inspecionar sua estrutura antes de desenhar o parser.
- Rodar `pdftotext -layout` no PDF real *antes* de escrever `parse_resolucao()` (em vez de confiar no pseudocódigo do Design) foi o que revelou os dois bugs reais documentados abaixo — nenhum dos dois apareceria testando só com texto sintético inventado.

### Technical

- **HTML e texto de PDF quebram parágrafos de formas fundamentalmente diferentes.** `ast_parser.py` (feature anterior) podia usar regex case-insensitive com segurança porque cada `<p>` do Planalto já era uma unidade semântica completa. Texto de `pdftotext -layout` quebra por largura de página, então uma referência cruzada em minúsculo ("art. 353") pode cair sozinha no início de uma linha e ser confundida com a definição de um artigo novo. A lição generaliza: **reaproveitar um regex de um parser de HTML para texto de PDF exige revalidar as premissas de contexto, não só copiar o padrão.**
- O padrão `aguardando_titulo_para` de `ast_parser.py` (usado para descartar o título que segue um cabeçalho de seção) generalizou direto para o parser de PDF, mesmo com títulos de Seção em Title Case (não all-caps como os de Capítulo) — confirma que esse é um padrão robusto do projeto, não algo acoplado a HTML.
- Parametrizar `executar_pipeline()` com um `parser` injetável (mudança pequena, aditiva) evitou duplicar toda a orquestração scrape→parse→chunk→embed→index só para trocar uma chamada de função — vale considerar esse tipo de parametrização desde o Design na próxima feature de fonte nova.

### Communication

- Corrigir a premissa do PDF ausente diretamente no DEFINE e no DESIGN (em vez de só mencionar em conversa) manteve os documentos como fonte de verdade — qualquer pessoa lendo só o DESIGN entende o motivo sem precisar do histórico da conversa.

### Tools & Libraries

- `pdftotext`/`pdftohtml` (poppler-utils) confirmaram ser suficientes para extração de PDF real sem nenhuma biblioteca Python — mesmo padrão de "binário de sistema contorna o bloqueio de pip" já usado implicitamente pelo projeto. CI precisou de um step novo (`apt-get install poppler-utils`) para não quebrar — vale lembrar disso para qualquer feature futura que dependa de binário de sistema em vez de pacote pip.
