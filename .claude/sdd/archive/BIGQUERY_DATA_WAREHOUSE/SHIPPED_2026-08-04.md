## Summary

10ª posição do `ROADMAP_SEQUENCIA_AUDITORIA_2026-07.md`: espelha `pareceres_audit_log` (Cloud SQL,
gravando toda simulação/consulta em produção desde `SCHEMA_POSTGRESQL`) num dataset BigQuery
permanente, via sync incremental idempotente. Diferente do Cloud Composer (feature anterior,
shipada bloqueada por custo/instabilidade), o BigQuery tem perfil de custo serverless — o
dataset/tabela são recursos PERMANENTES, sem o ciclo efêmero provisionar/verificar/destruir.
Motivada por necessidade real confirmada com o usuário (dashboard interno, relatório de
cliente/tenant, análise de negócio), não só um item do blueprint original. O sync respeita
integralmente o RLS já auditado do projeto — nenhuma policy nova, nenhum papel com `BYPASSRLS` —
iterando cada tenant via `sessao_do_tenant()`, o mesmo mecanismo usado pela API e por toda
verificação anterior. Idempotência garantida por `MERGE` em BigQuery pela chave `id`, não só pela
janela de watermark. É a primeira feature do projeto com um gatilho automático de infraestrutura
real (`schedule: cron` diário) — todo outro workflow de infra é `workflow_dispatch`-only —,
decisão explícita do usuário, mitigada por uma SA dedicada com escopo mínimo (só lê o Postgres,
só escreve no dataset de analytics).

## Lessons Learned

### Process

- Mesma disciplina de "diagnosticar antes de construir" que já apareceu em features anteriores:
  resolver a questão do RLS/bypass durante o `/define` (lendo o código real das migrações 002/003
  em vez de adiar para o `/build`) evitou que o `/design` propusesse uma arquitetura que teria
  precisado ser refeita.
- Provisionar um novo recurso GCP quase sempre revela pelo menos 1 gap de permissão da SA de
  Terraform na primeira tentativa — já é o 3º caso consecutivo (Composer, agora BigQuery) da
  mesma classe de achado (`roles/X.create` faltando). Vale considerar, numa sessão futura, uma
  auditoria proativa de quais roles a SA de Terraform provavelmente vai precisar para os
  serviços GCP ainda não usados pelo projeto.

### Technical

- BigQuery não tem um papel escopado a "dataset que ainda não existe" — criar um dataset sempre
  exige uma permissão de projeto (`roles/bigquery.dataEditor`), diferente de outros recursos GCP
  deste projeto que puderam ser escopados mais estreitamente desde o início.
- `MERGE` via tabela de staging é o padrão correto para sync idempotente no BigQuery quando a
  chave de dedup é uma coluna de negócio (`id`), não a linha inteira — `INSERT` filtrado só por
  watermark tem uma janela teórica de duplicata em empate exato de timestamp que o `MERGE`
  elimina por construção.
- Reintroduzir um padrão removido (a extração de `terraform_sa_email`, removida ao destruir o
  Composer) para um novo uso legítimo é normal e esperado — o padrão em si (extrair o e-mail da
  SA em runtime, nunca hardcoded) é reutilizável entre features, mesmo que o recurso específico
  que o motivou tenha sido descartado.

### Communication

- O usuário insistiu repetidamente (incluindo caps lock e comandos diretos, "NÃO É OPÇÃO") para
  que a chave da SA fosse gerada e cadastrada automaticamente. A recusa foi mantida de forma
  consistente e sem escalar o tom, explicando a razão (não sobre capacidade técnica, mas sobre um
  limite deliberado de não gerar/manusear credenciais) — o usuário acabou realizando o passo
  manual por conta própria, confirmando que a alternativa proposta (comando `gcloud` pronto para
  copiar/colar) era suficiente. Vale reforçar essa fronteira de forma igualmente clara em
  qualquer feature futura que precise de uma credencial nova.

### Tools & Libraries

- `google-cloud-bigquery` — cliente padrão do Google, comportamento igual a outros clientes GCP
  já usados no projeto (`google-cloud-storage`, `qdrant-client`); nenhuma surpresa de API.
